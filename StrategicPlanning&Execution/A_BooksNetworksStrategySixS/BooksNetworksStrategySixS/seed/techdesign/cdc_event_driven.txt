title: CDC and Event-Driven Integration
variant: Log-based change data capture to many consumers
summary: Change data capture reads a database transaction log and publishes every insert, update and delete as an event. Downstream services, search indexes, caches and the warehouse subscribe to these events, staying in sync without polling or dual writes.
when_to_use: Many systems need near real-time copies of operational data, and you want to avoid dual writes or heavy batch extracts.
when_not_to_use: There is a single consumer with relaxed freshness, or the source database cannot expose its log.
complexity: Medium
tags: cdc, debezium, event driven, outbox, kafka

@step
order: 1
text: The application commits data, and optionally an outbox event, in one transaction.
components: C1,C2

@step
order: 2
text: The database records the change in its transaction log.
components: C3

@step
order: 3
text: The CDC connector reads the log and publishes change events to the broker.
components: C4,C5

@step
order: 4
text: Stream transformers filter and enrich events.
components: C7

@step
order: 5
text: Sinks update the warehouse, search index and cache; services react to events.
components: C8,C9,C10,C11

@step
order: 6
text: Failed events go to the dead letter queue and monitoring watches lag.
components: C12,C13

@tradeoff
kind: pro
text: Near real-time sync without polling or touching application code paths.

@tradeoff
kind: pro
text: Decouples producers from many consumers.

@tradeoff
kind: con
text: Consumers see database-shaped events unless an outbox or transformation is added.

@tradeoff
kind: con
text: Needs careful handling of ordering, duplicates and schema changes.

@tradeoff
kind: risk
text: A stalled connector can make the source database retain log files and fill its disk.

@tradeoff
kind: cost
text: Broker and connector infrastructure to run.

@tradeoff
kind: scaling
text: Partition topics by key to preserve per-entity order and scale consumers in groups.
