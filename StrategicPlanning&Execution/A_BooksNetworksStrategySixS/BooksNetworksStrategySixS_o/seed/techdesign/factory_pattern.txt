design_type: factory_pattern
title: Factory Method Pattern
variant: Creator with product hierarchy
summary: Factory Method defines an interface for creating an object but lets subclasses decide which concrete class to instantiate. The client works only with the abstract creator and product types, so new product types can be added without changing client code.
when_to_use: The exact class of objects is only known at runtime or varies by configuration, and you want to keep creation logic out of client code.
when_not_to_use: There is only one product type that will never change; a plain constructor is simpler.
complexity: Low
tags: creational, gof, factory, polymorphism

@step
order: 1
text: The client picks a concrete creator, for example from configuration.
components: C7,C3

@step
order: 2
text: It calls the operation on the abstract creator.
components: C7,C1

@step
order: 3
text: The creator calls its factory method, which the subclass implements.
components: C1,C3

@step
order: 4
text: The subclass instantiates the concrete product.
components: C3,C5

@step

text: The creator uses the product only through the Product interface.

@tradeoff
kind: pro
text: Client code depends on abstractions, not concrete classes.

@tradeoff
kind: pro
text: New products are added without changing existing code (open/closed).

@tradeoff
kind: con
text: Adds a parallel hierarchy of creator classes.

@tradeoff
kind: con
text: Can be overkill when there are few product types.

@tradeoff
kind: risk
text: Overuse hides simple object creation behind needless indirection.

@tradeoff
kind: cost
text: More classes to write and maintain.

@tradeoff
kind: scaling
text: Combine with a registry or dependency injection when the number of products grows.
